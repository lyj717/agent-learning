## 一、开始前：这份计划的前提与三条铁律

### 前提假设
- 你已经能读懂并写出基础代码（任意语言），但 Python 不熟。先按 7 个单元补齐 Python 的语法差异与生态，细节留到项目里边做边补，配套练习见 **python-7天补齐清单.md**。
- 如果完全没写过代码，把 Python 补齐阶段延长到 3~4 周，再从第 1 周开始。
- 按每天约 3~5 小时安排；较重单元可以拆到多天，不要求周末额外投入 6~7 小时。
- 你有可用的模型 API。本仓库使用兼容 Chat Completions 的接口学习，参数支持与返回字段仍要核对实际服务商、模型和模式。

### 三条铁律（比学什么更重要）
1. **产出驱动**：新概念用小实验和亲手实现验证，保留足够的写代码与排错时间；不按代码行数验收。
2. **手写一遍再上框架**：Agent 的核心循环必须自己用纯 API 写过一次，之后再用 LangGraph / OpenAI Agents SDK 才不至于只会抄配置。
3. **每阶段一个可演示成果**：可以是同一项目的新版本。当天完成、订正通过、跨天独立复现分别记录；正式视频按学员安排在面试复习时补录。

### 立刻要做的环境准备（半天）
- 装 Python、编辑器和 Git；本机实际环境见根 README。容器环境在工程化阶段按需准备，不作为开始学习的前置任务。
- 建 GitHub 账号，配好 SSH key，学会 `add / commit / push / branch / PR` 五个动作。
- 把 API Key 存进 `.env`，学会用 `.gitignore` 防止密钥泄露（面试会看这个细节）。
- 建 `agent-learning` 仓库。AI 在当天验收收尾后本地提交，学员自行推送；提交记录用于追踪变化，不代替能力验收。

### Python 补齐阶段（第 0 周，7 天）

不要系统学 Python。你的目标是 7 天后能读懂并改写真实 Agent 项目的代码，方法是只补「差异点 + 生态」，其余遇到再学。

| 天 | 主题 | 产出 |
|---|---|---|
| Day 1 | 缩进语法、动态类型、f-string、真值判断 | 写代码不再打大括号 |
| Day 2 | list/dict/tuple/set、切片、推导式、解包 | 能正确处理消息集合，并解释循环与推导式的选择 |
| Day 3 | 函数、`*args/**kwargs`、lambda、类型注解 | 能给工具函数写规范的类型注解 |
| Day 4 | 类、`self`、模块导入、Pydantic | 能用 Pydantic 描述工具入参 |
| Day 5 | 文件、JSON、异常、虚拟环境、`.env`、logging | 能建干净环境，密钥不进代码、日志与版本库 |
| Day 6 | 生成器、装饰器、async/await、`asyncio.gather` | 看懂流式输出的实现 |
| Day 7 | 串烧实战：命令行 + 真实 API 调用 + 流式 + pytest | 一个能跑、有 README 的小项目 |

**其中三件事必须写熟，后面天天用**：f-string、字典与推导式、类型注解。

**明确跳过**：GUI、爬虫、Django/Flask 全栈、数据分析全家桶、并发底层原理、设计模式。这些对拿 Agent 岗位没有直接帮助。

## 三、逐周详细计划

### 第 0 周（下半段）：认知对齐（与 Python 补齐并行，2~3 天）

**要弄明白的四件事**
- Agent 和普通聊天机器人的区别：Agent 有目标、会自主选择工具、能循环迭代直到完成或放弃。
- Agent 和工作流（Workflow）的区别：工作流是固定步骤，Agent 是模型决定下一步。面试高频题。
- 一个 Agent 的最小组成：模型 + 系统提示词 + 工具 + 循环 + 记忆 + 终止条件。
- 这个岗位实际在做什么：接大模型 API，把公司业务拆成可被模型调用的工具，再解决准确性、成本、延迟、可靠性问题。

**动手**
- 注册一个模型 API，用 20 行代码发一次请求，打印返回内容。
- 把 temperature 分别设为 0 和 1.5，观察同一条 prompt 的输出差异，记录下来。

**检查点**：能用自己的话向外行解释「我和 ChatGPT 的区别是什么」。

---

### 第 1 周：LLM 基础与 API 熟练度

**知识点**
- token、上下文窗口、上下文长度与成本的关系、计费方式。
- system / user / assistant 三种角色的作用，以及为什么 system 提示词影响巨大。
- temperature、top_p、max_tokens 等参数的实际影响。
- 流式输出（streaming）的实现方式。
- 幻觉、知识截止、为什么必须靠检索和工具补足事实。

**动手项目：流式 CLI 聊天机器人**
- 支持多轮对话（自己维护 message 列表）。
- 支持流式打印、支持 `/clear` 清空上下文。
- 支持切换模型、打印本次消耗的 token 数和估算花费。
- 加一个简单的上下文裁剪策略（例如超过 N 轮就丢弃最早的消息）。

**检查点**：能解释「为什么上下文越用越贵」，以及长对话你是怎么做取舍的。

**推荐资料**：所选模型厂商的官方 API 文档（务必以官方文档为准，接口细节更新很快）。

---

### 第 2 周：结构化输出与工具调用

这一周是 Agent 开发的分水岭。工具调用（tool calling / function calling）不熟，后面全部无从谈起。

**知识点**
- JSON 模式与结构化输出的差别，以及怎么用 schema 约束模型输出。
- 工具调用的完整流程：定义 schema → 模型返回工具名和参数 → 你执行 → 把结果回填给模型 → 模型给最终答复。
- 模型返回的 JSON 解析失败怎么办（重试、修复提示、schema 校验）。
- Pydantic 做参数校验的写法。

**动手项目：结构化信息抽取器 + 工具箱**
- 从杂乱文本（简历、发票、新闻）里抽取出固定结构的 JSON。
- 给模型接上 3 个能执行的工具：模拟天气、计算器和 SQLite 查询；说明模拟快照与真实数据的边界。
- 有一个工具故意会报错，练习把错误信息回填给模型让它自己纠正。

**检查点**：白板画出一次工具调用的完整回合，说清「谁在什么时候执行了什么」。

---

### 第 3 周：Agent 核心循环（手写，不借助框架）

**知识点**
- ReAct 思路：思考 → 行动 → 观察 → 再思考，直到给出答案。
- 循环的终止条件：拿到最终答案 / 达到最大步数 / 超时或超预算。
- 提示词如何描述可用工具、如何要求模型按固定格式输出。
- 常见失控情形：无限循环、反复调用同一个工具、把工具报错当答案。
- 短期记忆（对话历史）与长期记忆（持久化存储）的区别。

**动手项目：不用任何框架的 ReAct Agent**
- 自己写主循环，自己解析模型输出，自己决定下一步。
- 工具集：本地文件检索、计算器、受限数值代码工具。当前实现不具备操作系统级隔离，不把它称为通用 Python 沙箱。
- 加日志，记录可观察的请求、工具名与参数、结果、用量、耗时及停止原因，不补写模型未提供的内部推理。
- 加最大步数限制和成本上限。

**检查点**：闭卷讲清消息回填与停止条件；换一个问题后仍能接起自己的循环，并根据轨迹定位一次失败。Day 26 拆成预算与停止判断、超时与重复调用两个单元，Day 27~28 整合，具体见本周 README。

**从这里开始积累评测案例**：复用练习里的正常完成、资料缺失、参数错误、连续失败、重复调用、预算耗尽情境。AI 搭检查工具，学员判断成功条件和实际结果，不另开一套重复作业。

**延伸阅读**：ReAct、Reflexion、Toolformer 这几篇经典论文的摘要，面试聊到「你了解哪些 agent 范式」时用得上。

### 第 4 周：框架、记忆与多步骤任务

**必做知识点**：只使用 LangGraph 学状态、节点、条件边、消息合并、检查点和人工确认；理解恢复时重复执行与幂等的关系。开工前用短题检查 `*args/**kwargs` 与异常分类，缺哪项补哪项。

**选修**：其他框架的对比、摘要记忆、向量记忆、结构化画像；不要求本阶段全部实现。

**动手项目：把第 3 周的 Agent 用 LangGraph 重写一遍**
- 用图的方式表达：模型节点、工具节点、条件边。
- 先用一种本地持久化方案存会话状态，支持中断后继续；不把检查点直接等同于长期用户记忆。
- 在教学数据上加一个有副作用的操作，确认前不执行；用执行次数验证恢复后不会重复生效。
- 用同一组问题比较手写版与框架版，说明状态、可调试性和维护上的取舍；代码量仅供参考。

**检查点**：能把图中的每一步对应回手写版；从中断恢复时，消息和工具执行次数符合预期。

### 第 5 周：RAG 基础

**知识点**
- 为什么需要 RAG：私有数据、事实准确性、可追溯引用。
- 完整链路：文档加载 → 切分 → 向量化 → 存储 → 检索 → 拼进提示词 → 生成带引用的答案。
- 必做：先用一种切分方式和一个向量库跑通；理解 chunk、元数据和来源编号。
- 选修：第二种切分策略、多轮指代改写；混合检索与重排留到下一阶段按问题选用。

**动手项目：文档问答 Agent**
- 把你自己的资料（技术文档、PDF、笔记）灌进去。
- 答案必须带原文引用和出处页码，不能引用就承认「没找到」。
- 同时由学员准备约 10 条「问题 + 期望来源/无答案」的小样本，保存改动前基线。资料先选可直接读取的文本或文本型 PDF，复杂扫描件解析作为选修。

**检查点**：能区分检索未命中、生成答错、引用不支持结论；比较小资料全量放入上下文和检索方案的取舍，不背「长上下文永远不能替代检索」的绝对结论。

### 第 6 周：高级检索与检索评测

**必做知识点**：区分命中率、Recall@k 和 Precision@k；按检索、生成、引用三个层次归类失败。根据真实失败选择混合检索、切分调整或重排中的一项，再决定是否继续优化。

**选修**：查询改写、多查询、HyDE、父子块、上下文压缩、时间加权与 nDCG。涉及不同用户的数据时必须处理权限过滤，不把权限当效果优化的可选开关。

**动手项目：给上周的 RAG 加评测**
- 从上阶段样本逐步扩展到 30~50 条，保留没有用于反复调参的一部分作为留出检查；样本和期望来源由学员准备，AI 不代填。
- 实现评测脚本，明确分母与判分规则，分别报告检索、答案、引用、成本和延迟。
- 必做一组控制变量对比，保留没有提升或变差的结果；第二、三组按失败证据与时间选做，不为凑表强行接新方法。

**检查点**：能用数据说明改动影响了哪类问题、收益与代价是什么；效果未提升也是有效结论，不能更换判分口径来制造提升。

### 第 7 周：工程化与可观测性

**知识点**
- FastAPI 写服务端：同步/异步、流式响应（SSE）、请求校验。
- 可观测性：调用链追踪、token 与成本统计、出错率、延迟分位数（P50/P95）。
- 工具：LangSmith、Langfuse、OpenTelemetry 等 trace 方案的用途。
- 必做限流、重试与并发上限；缓存与路由优化留到下一阶段。
- 安全：提示词注入、工具越权、密钥管理、输出内容过滤。

**动手项目：把 Agent 变成真正的服务**
- 按接口与会话隔离 → 流式与断开处理 → trace → 部署的顺序，每块能独立验证后再接下一块。
- 最简前端能对话、看引用和耗时即可，界面打磨作为选修。
- trace 沿用前面已有的轨迹字段，选择一种工具；检查密钥、个人数据不会被原样记录。
- 准备容器环境并打包，验证 README 的安装与启动步骤；尚未验证的部署能力如实标记。

**检查点**：从一次失败请求找到对应轨迹；按 1、5、10 等梯度逐步测试并发，结合额度与限流选择停止点，报告实际范围和瓶颈。假模型压测与真实服务商测试分开记录，不强行追求 50 并发。

### 第 8 周：评测、可靠性与成本

**知识点**
- 评测方法：规则匹配、LLM-as-judge、人工标注的取舍与坑。
- 回归测试：改了提示词或模型后，怎么确保没有变差。
- 成本优化：模型分级路由（简单任务用小模型）、上下文压缩、结果缓存、批量处理。
- 延迟优化：并行工具调用、流式首字延迟、预取。
- 失败模式清单：无限循环、工具误用、幻觉引用、格式崩坏、注入攻击。

**动手项目：给项目加评测与 CI**
- 把已有确定性检查接入 GitHub Actions；真实模型评测采用明确的手动入口或受控预算，不让每次提交都自动花费额度。
- 在已有人工判分基础上学习模型裁判，并抽样比较分歧；按瓶颈选择一个成本或延迟优化。
- AI 继续维护根 `FAILURES.md`，学员从真实记录中选择能讲清的故障，不为了数量制造案例。

**检查点**：面试官问「怎么保证 Agent 上线不出事」，你能拿出评测集、trace 和失败清单三件套。

### 第 9 周：进阶方向（只选一项完成，其余选修）

**选项 A｜MCP（Model Context Protocol）**
- 理解它的定位：用统一协议连接外部数据和工具。可复用此前写过的检索或数据库工具，避免另起一套业务系统。
- 动手：自己写一个 MCP Server（例如接公司内部文件、数据库或某个 API），发布到 GitHub，写好 README。

**选项 B｜多智能体编排**
- 何时真的需要多个 Agent（角色分工、并行检索、评审-生成分离），何时只是把简单问题搞复杂。
- 动手：做一个「研究员 + 批评者 + 汇总者」的多角色协作流程，并把每步 trace 展示出来。

**选项 C｜语音 / 实时交互**
- 实时语音链路、打断处理、延迟预算。适合做差异化 demo。

**选项 D｜模型微调与蒸馏**
- 了解 SFT、LoRA、偏好优化的大致流程与代价，知道「大多数业务问题不该用微调解决」。会用即可，不必深挖。

**检查点**：至少有一个方向做到「别人可以用」的程度，而不是只跑通 demo。

### 第 10 周：作品集定型

整理两个主要项目与一个小工具，沿用已有成果，不要求新建三个同等规模的系统。阶段内持续保留真实轨迹与简短说明，正式视频在面试复习时补录。

| 项目 | 展示能力 | 硬性要求 |
|---|---|---|
| 复杂工具型 Agent | 工具设计、循环控制、错误恢复 | 接入能执行的工具，标清真实/模拟数据；有失败路径与 trace |
| 文档知识库问答 | RAG 全链路、评测意识 | 带引用、有评测集、至少一组有依据的对比实验 |
| MCP Server 或已有能力拆出的开源小工具 | 工程规范、复用能力 | 有相关测试、CI、清晰 README；有实际 issue/PR 再展示，不凑数量 |

**每个项目必须包含**
- 一句话说明「解决谁的什么问题」。
- 架构图（一张清晰的图胜过千字说明）。
- 真实运行方式与讲解提纲；面试复习时补录 3 分钟以内的视频，主要项目至少一个完成可供他人体验的演示。
- 关键取舍说明：为什么不选另一个方案，成本与延迟如何。
- 已知缺陷与下一步计划（诚实说明局限性反而加分）。

### 第 12 周：面试冲刺与复盘

- 每场面试结束后 1 小时内写复盘：被问倒的问题、答得含糊的地方、对方的业务痛点。

## 四、每日安排与复习

统一使用 [日程表的时间块与跨天复习规则](21天详细日程表.md)，这里不重复维护另一份时间表。一天以一个主要新机制为主；较早完成时先做变式或复习，不自动追加整套新内容。

阶段复盘先由学员不看资料讲，再对照面试题与已有代码。首次学习可给分步提示；阶段整合和跨天复现减少实现提示，但接口、输入输出和验收标准仍必须清楚。

---

## 五、时间变化时的取舍

- 时间较少：先删选修、额外框架和界面打磨，再延长阶段；保留关键实现、失败路径、独立复现与必要验证。
- 时间较多：先用未见过的输入验证掌握程度，确认后再连做较轻单元；不按学习时长等比例压缩所有阶段。
- 基础不足：针对实际卡点补 Python 与 Web 概念，补完再接回当前阶段，不为凑日期跳过先修知识。
- 总工期随真实进度调整。完成课程不能保证某日拿到面试或 offer，投递反馈由求职阶段单独记录。

---

## 六、避坑清单

1. 收藏材料却没有亲手验证。→ 每个主要新概念都用小实验或实现验证。
2. 只会调框架，说不清底层发生了什么。→ 第 3 周的手写循环不许跳过。
3. 项目没有评测数据。→ 没有指标的优化只是感觉，面试官一戳就破。
4. 只做「能跑通」的 demo，没处理失败、成本、并发。→ 工程细节才是招聘方真正要买的。
5. 简历写「熟悉大模型、了解 Agent」却拿不出项目。→ 用项目和数字说话。
6. 追新框架追到晕。→ 优先理解工具调用、循环、检索与评测，再查当前框架如何表达它们。
7. 只在本地跑，从不部署。→ 至少要有一个可以点开链接体验的 demo。
8. 面试前才开始回忆项目。→ 阶段末先做口头讲解并保留轨迹，正式视频在面试复习时补录。
9. 等「学完 Python」才动手。→ 先补当前任务的必要语法，其余在项目里按需学。

## 七、阶段自查（并入本周 README，不新增打卡表）

- 我能否在减少提示后完成核心实现，并解释消息或数据怎么流动？
- 隔 2~3 天是否做过一次独立复现？还需要什么提示？
- 是否检查正常、边界和失败路径，能从输出指出依据？
- 是否用自己的项目讲清一个设计取舍和一个真实故障？
- 当前入口、已知限制和下一步是否准确？AI 是否完成收尾检查？

尚未复验就记录「待复验」，发现薄弱点就缩小下一单元范围；不为了打勾补造证据。
