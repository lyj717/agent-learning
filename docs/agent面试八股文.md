## 二、第一部分：概念与判断

### Q1. Agent 和聊天机器人、工作流的区别是什么？

**一句话**：聊天机器人是「你说一句它答一句」，工作流是「步骤由人写死」，Agent 是「目标给定，下一步由模型自己决定，并且能循环执行直到完成」。

**展开**

- 聊天机器人：无状态或弱状态，输入输出一轮结束，不会主动做事。
- 工作流：流程固定，比如「先分类 → 再检索 → 再生成」，路径可控、可预测、好测试。本质是**用代码编排模型**。
- Agent：模型自己选择调用哪个工具、调几次、什么时候停。本质是**用模型编排代码**。

**加分点**：真正落地时大多数场景是混合的——主流程用工作流保证稳定，在某个节点让 Agent 自主决策。**上来就说「用多智能体解决」通常不是好答案，先说「能不能用工作流解决」才是成熟的判断。**

### Q2. 什么时候不该用 Agent？

**一句话**：当任务能用确定性代码解决、或者对延迟和成本极度敏感、或者出错代价高到无法接受时，都不该用 Agent。

**展开**

- 流程固定且分支有限 → 用工作流，更稳更便宜。
- 需要精确计算或强一致 → 用代码，模型只负责理解意图和表达结果。
- 延迟预算很紧（比如几百毫秒内）→ Agent 的多轮循环天然做不到。
- 高风险且无法自动验证（比如直接执行转账）→ 必须有确定性校验或人工确认。

**加分点**：说一句「我判断要不要上 Agent 的标准是：**步骤是否可预先枚举**、**失败是否可自动检测**、**成本和延迟预算是否允许循环**」。这三个标准比背定义有说服力得多。

### Q3. 常见的 Agent 架构范式有哪些？

**一句话**：主流是 ReAct（边想边做）、Plan-and-Execute（先规划再执行）、以及在这两者之上的反思与多智能体协作。

**展开**

- **ReAct**：模型交替输出「思考」和「行动」，你执行行动并把结果作为「观察」回填，循环到得出答案。优点是灵活、实现简单；缺点是步数不可控、容易绕圈。
- **Plan-and-Execute**：先让模型出计划，再逐步执行，执行中可以重规划。优点是总步数可控、便于并行；缺点是计划质量差时整体跑偏。
- **Reflexion / 自我反思**：把失败结果和自己的错误当作经验存下来，下次改进。适合有明确反馈信号的场景。
- **多智能体**：分角色协作（研究员、批评者、汇总者）。优点是能隔离上下文、并行探索；缺点是成本和延迟成倍增长、错误会传播。

**加分点**：主动补一句取舍——「我在项目里优先用 ReAct 加步数上限，因为实现简单、可观测；只有当任务能明显拆成并行子任务时才上多智能体」。

### Q4. Agent 的终止条件怎么设计？

**一句话**：至少四道闸：拿到最终答案、达到最大步数、超出时间或成本预算、连续重复调用同一工具。

**展开**

- 正常终止：模型给出不含工具调用的最终答复。
- 步数上限：通常 5~15 步，按任务复杂度定。
- 预算上限：token 总量或金额上限，超了就降级或中止。
- 死循环检测：同一工具同一参数连续调用两次以上，直接中断并返回已有信息。
- 异常终止：工具连续失败达到阈值，走兜底回答而不是继续重试。

**加分点**：说清「终止条件要写在代码里，不能靠提示词求模型自己停」。**靠提示词约束是有概率失效的，靠代码约束是确定性的。**

### Q5. Agent 为什么会产生幻觉，怎么缓解？

**一句话**：模型本质是在预测下一个 token，没有事实数据库，也没有「我不知道」的默认倾向；缓解要靠检索、工具、引用约束和校验。

**展开**

- 事实类问题 → 用 RAG 把原文喂进去，要求答案必须引用出处。
- 时效类问题 → 用搜索工具，不要依赖模型内部知识。
- 计算与精确操作 → 交给代码执行，不让模型心算。
- 输出约束 → 结构化输出 + 校验失败就重试或降级。
- 提示词层面 → 明确说「资料里没有就回答没找到」，并给一个示例。

**加分点**：承认「不可能完全消除，只能降低并检测」。然后给出检测手段：引用溯源、事实一致性校验、把不确定的答案交给人工复核。

### Q6. 你怎么评估一个 Agent 需求值不值得做？

**一句话**：看三件事——输入是否自然语言且多变、步骤是否无法预先枚举、错误成本是否可接受。

**展开**

- 值得做：输入形式多样（用户表达千奇百怪）、处理路径因情况而异、出错可以人工兜底。
- 不值得做：输入高度结构化、规则明确、出错要赔钱。
- 还要算一笔账：现有方案的成本和效果是多少，Agent 方案能不能在可接受的成本下明显超过它。

**加分点**：加一句「我会先做一个最小可行版本，用小样本验证效果上限，再决定要不要投入工程化」。这句话体现了你不盲目追技术。

## 三、第二部分：工具调用

### Q7. 工具调用的完整流程是什么？

**一句话**：你在请求里带上工具的 schema，模型决定调用哪个工具并给出参数，**你的代码**执行工具，把结果作为一条消息回填，模型再基于结果生成答复。

**展开（这是必背题，必须能按顺序讲出来）**

1. 你定义工具：名字、描述、参数 schema。
2. 你把工具定义和用户消息一起发给模型。
3. 模型返回的不是文字，而是「我要调用某个工具，参数是这些」。
4. **你的程序执行这个工具**（模型自己不执行任何东西，这一步最关键）。
5. 你把执行结果作为工具角色的消息追加到对话历史里。
6. 再发一次请求，模型基于结果生成最终答复。
7. 如果结果是「模型又要求调用工具」，就重复第 3~6 步。

**加分点**：强调「**模型只负责决策，执行永远在你的代码里**」。这句话能证明你真正理解机制，而不是把 SDK 当黑盒。

### Q8. 工具的描述怎么写才让模型选对？

**一句话**：名字要动词化且具体，描述要说明「什么时候用它」而不只是「它是什么」，参数要有类型和取值范围。

**展开**

- 名字：`search_orders` 比 `query` 好，一眼看出做什么。
- 描述：写清使用场景和边界，例如「按订单号查订单详情。用于用户提供了订单号的场景；如果要按人名查，用 find_orders_by_customer」。
- 参数：每个参数都要说明含义、格式和示例。
- 参数越少越好，能设默认值就设默认值。
- 工具之间**职责不要重叠**，两个工具都能干同一件事时模型就容易选错。

**加分点**：说「我遇到过工具选错的问题，排查后发现是两个工具的描述重叠，改成明确写清各自的适用场景后就解决了」。有具体案例比背原则强。

### Q9. 工具执行报错了怎么办？

**一句话**：不要直接抛给用户，要把错误信息作为观察结果回填给模型，让它自己调整参数重试，同时设重试上限。

**展开**

- 错误信息要写清楚：缺什么参数、参数格式要求是什么。
- 明确告诉模型「这是错误，请修正后重试」。
- 设最大重试次数（通常 2~3 次），防止无限试错。
- 有些错误不该重试：权限不足、资源不存在，重试多少次都一样，直接走兜底。
- 重试仍失败时，给出诚实的兜底回答，而不是编一个结果。

**加分点**：区分「可重试错误」和「不可重试错误」。很多人只答「重试」，能区分这两类说明你有工程判断。

### Q10. 模型能一次调用多个工具吗？

**一句话**：能。同一轮里模型可以返回多个工具调用请求，你应该并发执行它们，再把所有结果一起回填。

**展开**

- 并发执行用 `asyncio.gather`，能显著缩短多工具场景的总耗时。
- 要注意工具之间是否有依赖：有依赖就必须串行，没依赖才能并行。
- 回填时要保证每个结果和对应的调用 ID 配对，顺序错了模型会误解。

**加分点**：提醒「并发会放大限流风险，要加并发上限和对失败项的单独处理」。

### Q11. 工具的数量应该控制在多少？

**一句话**：同一轮里给模型的工具不要太多，五到十个是可维护范围；工具多了要么分组路由，要么用工具检索先筛一遍。

**展开**

- 工具越多，模型的注意力越分散，选错概率越高。
- 提示词长度也会膨胀，直接推高成本和延迟。
- 常见做法：按场景分组（客服组、订单组），先让模型选组再选工具。
- 或做「工具检索」：用向量检索从几十个工具里先找出最相关的几个再给模型。

**加分点**：说「工具数量本身不是问题，**语义重叠才是问题**」。

### Q12. 结构化输出和普通的 JSON 模式有什么区别？

**一句话**：JSON 模式只保证输出是合法 JSON，结构化输出还能保证符合你给的 schema，也就是字段名、类型、必填项都对。

**展开**

- 普通 JSON 模式：模型可能少字段、类型写错、多塞字段。
- 结构化输出：底层通过约束解码，让生成结果在格式上必然合法。
- 即便如此也要做业务校验：格式对了不代表内容对。
- 用 Pydantic 之类的工具接收返回值，校验失败就带错误信息重试。

**加分点**：说「格式正确性和语义正确性是两件事，前者能靠 schema 保证，后者只能靠评测」。

### Q13. 工具怎么设计得更安全？

**一句话**：最小权限、参数白名单、危险操作二次确认、所有操作留审计日志。

**展开**

- 最小权限：查订单的工具就不要有删订单的权限。
- 参数校验：模型给的参数一定要当不可信输入处理，做白名单校验，不要拼 SQL。
- 危险操作：删除、支付、发消息这类操作要走人工确认。
- 幂等：给写操作带幂等键，避免重试时重复下单。
- 审计：记录谁在什么时间通过哪个 Agent 调用了什么工具、参数是什么。

**加分点**：「把模型的输出当成用户输入来校验」——这句话点破了很多人忽略的风险。

## 四、第三部分：上下文与提示词

### Q14. 上下文窗口越来越大，为什么还要学上下文管理？

**一句话**：因为长不等于好用——成本线性上涨、延迟变高、关键信息会被淹没，而且「中间遗忘」是普遍现象。

**展开**

- 成本：输入 token 通常按量计费，上下文越长每一轮都越贵。
- 延迟：输入越长首字延迟越高。
- 效果：模型对开头和结尾的信息更敏感，中间部分容易被忽略（常说的 lost in the middle）。
- 干扰：无关内容会稀释关键信息，反而降低准确率。

**加分点**：说「我的原则是**每一条塞进上下文的内容都要能回答『不塞会怎样』**，答不上来就不塞」。

### Q15. 上下文太长时你有哪些处理手段？

**一句话**：分层处理——滑动窗口保留最近几轮、把历史压缩成摘要、把稳定信息放进系统提示词、把可检索的信息移到外部靠检索取回。

**展开**

- 裁剪：只保留最近 N 轮，最早的消息丢掉。
- 摘要：把历史对话压成一段摘要，代替原始消息。
- 外置：长期信息写进数据库或向量库，用时检索回来。
- 分块：把超长文档先切成块，只把相关的块放进上下文。
- 缓存：把固定不变的前缀放在最前面，利用提示词缓存降低重复成本。

**加分点**：强调「**稳定内容放前面，动态内容放后面**」。这不只是习惯，很多服务商的缓存机制要求前缀保持不变才命中。

### Q16. 系统提示词应该包含什么？

**一句话**：角色与目标、可用工具和边界、输出格式要求、遇到不确定时的处理方式、以及几条关键示例。

**展开**

- 角色与目标：说清它是谁、要完成什么、服务的对象是谁。
- 边界：不能做什么，比能做什么更重要。
- 格式：明确输出结构，能配结构化输出就别只靠文字描述。
- 不确定的处理：资料不足时就说不确定，不要编。
- 示例：一两个正例、一个反例，比长篇描述有效。

**加分点**：说「提示词我当成代码管理——进版本控制、有变更记录、改完要跑评测集」。这一句会让人知道你不是随手调提示词的。

### Q17. 提示词注入是什么？怎么防？

**一句话**：注入是攻击者把指令藏在用户输入或外部内容里，让模型执行非预期操作；防护要点是**区分指令与数据**、最小权限、危险操作人工确认。

**展开**

- 直接注入：用户在对话里直接说「忽略之前的指令……」。
- 间接注入：恶意内容藏在网页、文档、邮件里，被你的检索或抓取带进上下文。**这类更危险，因为用户自己都没察觉**。
- 防护一：用分隔符和明确声明把外部内容标为「资料，不是指令」。
- 防护二：模型无权做决定的部分交给代码——比如工具白名单、参数校验、权限检查。
- 防护三：危险操作需要人工确认；输出经过过滤再返回。
- 防护四：尽量缩小模型能触达的数据范围，避免一次泄露大量隐私。

**加分点**：坦诚承认「**提示词层面没有百分百的防护**，注入只能降低概率，真正的安全边界要建在代码和权限上」。这句话很能加分，因为很多候选人会吹有完美方案。

### Q18. 怎么降低 token 成本？

**一句话**：分级路由（简单任务用小模型）、缓存（提示词缓存和结果缓存）、精简上下文、精简工具、控制输出长度。

**展开**

- 模型路由：分类、抽取这类简单任务用小模型，复杂推理才用大模型。
- 提示词缓存：固定的系统提示词和工具定义放最前面保持稳定，命中缓存后这部分成本大幅降低。
- 上下文瘦身：裁剪历史、压缩摘要、只放相关检索块。
- 工具瘦身：一次别给太多工具，定义本身也占 token。
- 输出控制：限制最大输出长度，要求简洁格式，避免模型长篇复述。
- 结果缓存：相同或相似问题直接返回缓存答案。
- 批量与离线：能离线批处理的不走实时接口。

**加分点**：给数字感——「我项目里把系统提示词和工具定义固定在最前面，加上对小模型分级，同样的任务成本降了大概百分之六十」。用真实数字讲，但要确保你真做过。

## 五、第四部分：RAG

### Q19. 完整讲一下 RAG 的链路。

**一句话**：文档加载 → 切分 → 向量化 → 存入向量库 → 检索 → 重排 → 拼进提示词 → 生成带引用的答案。

**展开**

- 加载：支持 PDF、网页、数据库、文档系统，要处理各种脏格式。
- 切分：按长度或结构切块，块之间留重叠避免切断语义。
- 向量化：用嵌入模型把每个块变成向量。
- 存储：向量库建索引，支持近似最近邻检索。
- 检索：把用户问题也向量化，找出最相似的若干块。
- 重排：用更精确的模型对候选块重新排序，取最相关的几个。
- 生成：把选中的块和问题一起给模型，要求它只依据这些资料回答并给出出处。

**加分点**：指出**最容易出问题的是切分和检索，而不是生成**。很多人会本能地怪模型，其实九成问题出在前半段。

### Q20. 切分策略怎么选？

**一句话**：优先按文档自身结构（标题、段落、表格）切，结构不可用时按长度切并留重叠，检索效果好坏的差别很大。

**展开**

- 固定长度切分：简单，但可能切断句子和上下文。
- 递归切分：按段落、句子逐级尝试，尽量在自然边界断开。
- 语义切分：按语义相似度变化找边界，效果好但更慢更贵。
- 父子块（小检索、大生成）：用小块做检索命中率高，命中后把它所属的大块喂给模型，兼顾精度和上下文完整性。
- 重叠窗口：相邻块留 10%~20% 重叠，避免答案被切在两块中间。

**加分点**：说「切分大小要按数据类型调——合同和 API 文档的最佳块大小完全不同，我会用测试集实测而不是拍脑袋」。

### Q21. 为什么需要混合检索？

**一句话**：向量检索擅长语义相似，关键词检索擅长精确匹配；两者互补，融合后效果通常更好。

**展开**

- 向量检索：理解同义表达（「怎么退钱」能匹配到「退款流程」），但对专有名词、型号、编号不敏感。
- 关键词检索（BM25）：精确匹配词汇，对错别字和同义词无能为力。
- 融合方式：加权求和，或者用 RRF（倒数排名融合）——按每个结果在两个榜单里的名次算分再合并，不需要调权重，实现简单且稳健。

**加分点**：提一句 RRF 的公式 `分数 = Σ 1/(k + 排名)`，k 一般取 60。能说出这个细节，说明你真实现过。

### Q22. 重排（rerank）的作用和代价？

**一句话**：重排用更精确的模型对候选块重新打分排序，能明显提升精度，代价是额外的延迟和成本。

**展开**

- 原理：向量检索是「问题向量」和「文档向量」各自算好再比距离（双塔），快但精度有限；重排是让问题和文档一起过模型（交叉编码），精度高但慢。
- 用法：先召回几十个候选，再重排取前几个。不要让重排处理全量数据。
- 收益：召回率高的前提下，重排主要提升「排在最前面的是不是最相关的」。
- 代价：增加一次模型调用，延迟上升；数据量大时要考虑缓存和超时降级。

**加分点**：说「我的判断标准是先看召回够不够，如果召回里根本没有正确答案，重排再强也没用——**先修召回，再修排序**」。

### Q23. 用户问题和文档表述差异很大时怎么办？

**一句话**：做查询改写——多查询改写、假设性文档生成（HyDE）、结合对话历史补全指代。

**展开**

- 多查询改写：让模型把一个问题改写成几个不同表述，分别检索后合并结果。
- HyDE：先让模型生成一段「假想的答案」，用这段假答案的向量去检索，往往比用原问题的向量更接近真实答案的表述。
- 指代补全：多轮对话里「它」「那个」需要结合历史补成完整问题，否则检索必然失败。
- 拆解：复杂问题先拆成多个子问题，分别检索再综合。

**加分点**：提醒「查询改写会引入额外的一次模型调用，等于用延迟换效果，要按场景权衡」。

### Q24. 怎么让答案带可靠的引用？

**一句话**：给每个检索块编号，要求模型在句子里标注来源编号，再在代码层校验编号是否真实存在，最后渲染成可点击的出处。

**展开**

- 检索时给每个块一个 ID 和来源信息（文件名、页码）。
- 提示词里要求「每句话后面标注来源编号，没有依据就不要写」。
- 代码层校验：模型引用的编号必须在你给的块里，出现不存在的编号就标记为不可信或重试。
- 前端展示：点击引用能跳到原文位置，这是用户建立信任的关键。

**加分点**：说「引用不许由模型自由生成，**必须是它从我们给的材料里选**」。这是把幻觉关在门外的实用手段。

### Q25. 检索不到相关内容时应该怎么处理？

**一句话**：明确说没找到，并给出替代路径；绝不能编一个看起来合理的答案。

**展开**

- 设置相关性阈值，低于阈值就不进生成环节。
- 提示词里明确写「资料不足时回答：知识库里没有找到相关内容」，并给示例。
- 兜底策略：建议换个说法、给出相关但不完全匹配的条目、或转人工。
- 监控这个比例：兜底率突然升高，说明文档或检索环节出了问题。

**加分点**：把「拒答率」当指标监控起来，说明你有产品意识，不只是做技术。

### Q26. 文档更新了怎么办？

**一句话**：按文档 ID 做增量更新——重新切分向量化并覆盖旧数据，同时定期做全量重建。

**展开**

- 给每个块带上文档 ID 和版本号，更新时先删旧块再插新块。
- 用内容哈希判断是否真的变了，避免无意义重算。
- 索引重建要能不停机进行（建新索引再切换）。
- 元数据保留更新时间，检索时可以给新内容加权。
- 删除场景要处理：文档删了，对应的向量块也必须删干净，否则会检索到已作废的信息。

**加分点**：提到「删除比更新更容易被忽略，**检索到已删除的文档是很容易踩的坑**」。

### Q27. 多租户场景下 RAG 要注意什么？

**一句话**：权限过滤必须发生在检索阶段，而不是检索之后再过滤。

**展开**

- 每个块带上租户或部门的权限标签。
- 检索时带上过滤条件（元数据过滤），只在自己的数据范围内搜。
- 不要在「检索完再筛掉无权的内容」——那样既浪费算力，也可能因为结果数量不对而泄露信息存在性。
- 日志和缓存也要隔离，避免跨租户串数据。

**加分点**：你会说「我会在测试里专门构造一个跨租户检索的用例，确保返回结果里绝不出现别人的数据」。这体现的是安全和测试意识。

### Q28. 长上下文模型能取代 RAG 吗？

**一句话**：不能。RAG 解决的不只是上下文长度问题，还有成本、延迟、新鲜度、权限和可追溯性。

**展开**

- 成本与延迟：全量塞入每次都要付那份钱，延迟也更高。
- 新鲜度：知识库可以每天更新，模型权重不会。
- 权限：检索阶段就能做数据隔离，全量塞入很难保证。
- 精度：无关内容混在上下文里会干扰模型，反而降低准确率。
- 可追溯：RAG 天然能给出出处。

**加分点**：说「两者可以结合——**长上下文减少了切分压力，但不能替代检索的权限和新鲜度能力**」。这是比较成熟的判断。

## 六、第五部分：记忆

### Q29. Agent 的记忆怎么设计？

**一句话**：分三层——会话内的短期记忆、跨会话的长期记忆、以及结构化的用户画像，各自的存储和更新策略不同。

**展开**

- 短期：当前会话的消息列表，直接放在上下文中，超长时裁剪或摘要。
- 长期：把重要信息（偏好、结论、事实）写进数据库或向量库，需要时检索回来。
- 画像：结构化字段（用户是谁、偏好什么、做过什么），比一段自由文本更好用。
- 写入策略：不是所有内容都值得记，要判断「这条信息以后还有用吗」。

**加分点**：说「记忆最大的坑是**记了太多没用的东西**，结果每次都把上下文塞满噪声。我会对写入做过滤，而不是无脑全存」。

### Q30. 记忆什么时候写入、什么时候读取？

**一句话**：读写分离——写入在会话中或结束时按重要性筛选，读取在每轮开始按当前问题检索相关记忆。

**展开**

- 写入时机：会话结束批量提炼、用户明确说「记住」、检测到关键偏好或事实时。
- 写入内容：去重、去掉过时信息、保留时间和来源。
- 读取方式：用当前问题做检索，只取最相关的几条，不要全量注入。
- 冲突处理：新信息与旧信息冲突时，按时间或置信度覆盖，并保留历史。

**加分点**：提到「记忆也需要评测——我会检查它到底提升了多少效果，避免为了做记忆而做记忆」。

### Q31. 会话状态怎么在多实例部署下保持？

**一句话**：服务做成无状态的，状态外置到数据库或缓存里，用会话 ID 关联；不要放在进程内存里。

**展开**

- 进程内存里的状态，一旦扩容到多个实例或重启就丢了。
- 每次请求带上会话 ID，服务根据 ID 读取和写回状态。
- 并发同一会话要用乐观锁或队列串行化，避免两个请求互相覆盖。
- 状态要有过期策略，否则存储会无限增长。

**加分点**：说「我会把状态管理抽象成接口，本地开发用 SQLite，生产换 Postgres，代码不用改」。

## 七、第六部分：评测

### Q32. 你怎么评测一个 Agent？

**一句话**：先定指标，再建测试集，然后分层评测——检索层、生成层、任务层，最后接进 CI 做回归。

**展开**

- 定指标：任务成功率、答案正确率、引用准确率、平均步数、平均成本、P95 延迟。
- 建测试集：从真实使用里采样，标注期望答案或期望来源；困难的边界情况要专门补进去。
- 分层：检索看召回率和命中率，生成看忠实度和相关性，任务看整体是否完成。
- 自动化：规则匹配能判的就别用模型，需要主观判断的用模型评分加人工抽检。
- 回归：每次改提示词或换模型都跑一遍，防止悄悄变差。

**加分点**：说「**没有测试集的优化都是凭感觉**，我项目里先建 30 到 50 条测试集，之后每次改动都有数据支撑」。

### Q33. 用模型当裁判（LLM-as-judge）有什么坑？

**一句话**：模型裁判有位置偏好、长度偏好、自我偏好，需要靠明确评分标准和交叉校验来降低偏差。

**展开**

- 位置偏好：比较两个答案时，倾向于选先出现的那个。解决：交换顺序各评一次。
- 长度偏好：倾向于给更长的答案高分。解决：评分标准里明确「简洁且正确不扣分」。
- 自我偏好：模型倾向给自己生成的答案高分。解决：用不同的模型做裁判，或与人工标注对齐验证。
- 评分标准要具体到可判断，比如「是否引用了资料、是否有事实错误」，而不是「好不好」。
- 用一批人工标注过的样本，检验模型裁判和人工的一致率。

**加分点**：说「模型裁判适合做**大规模粗筛**，关键结论我会人工复核」。定位清楚比否认偏差更专业。

### Q34. 常用指标有哪些？

**一句话**：检索层看召回率、命中率、MRR、nDCG；生成层看忠实度、答案相关性、引用准确率；任务层看成功率和成本延迟。

**展开**

- 召回率@k：正确答案有没有出现在前 k 个结果里。**这是最该盯的指标**，因为召回不到就没救。
- 精确率@k：前 k 个里有多少是相关的。
- MRR：第一个正确结果的排名倒数，衡量「排得够不够前」。
- nDCG：考虑排序位置和相关性等级的加权指标，适合多级相关性。
- 忠实度：答案是否完全基于给定资料，没有编造。
- 引用准确率：标注的出处是否真的支持那句话。
- 任务成功率：端到端是否真的完成了用户目标。

**加分点**：说「指标要先对齐业务——客服场景可能更在意**答错率**而不是平均分」。

### Q35. 改动提示词后怎么保证没变差？

**一句话**：跑回归测试——固定测试集、固定参数、对比改动前后的各项指标，差异超出阈值就拦住。

**展开**

- 测试集固定，避免「用新数据证明自己变好了」。
- 记录改动前后的完整指标表，而不只盯着一个数。
- 关注分项的变化：总体变好但某一类问题变差，可能埋了隐患。
- 接进 CI，提交时自动跑，输出对比报告。
- 保留历史版本，效果不好能立刻回滚。

**加分点**：说「提示词我会当代码管理，改动用提交记录，附上评测结果」。这句话非常加分。

### Q36. 线上怎么发现问题？

**一句话**：全链路追踪 + 关键指标监控 + 用户反馈回收 + 定期人工抽检。

**展开**

- 追踪：每次调用都记录模型版本、提示词版本、工具调用、token、耗时、结果。
- 监控：成功率、错误率、兜底率、成本、P95 延迟；设阈值告警。
- 反馈：点赞点踩、转人工率，作为效果的代理指标。
- 抽检：定期抽样人工看，特别注意那些「看起来成功但其实答错」的案例。
- 灰度：新版本先小流量验证再全量。

**加分点**：说「我会专门盯**静默失败**——用户没投诉但答案其实是错的，这类只能靠抽检和评测集发现」。

## 八、第七部分：工程与性能

### Q37. 为什么 Agent 开发要用异步？

**一句话**：因为绝大部分时间在等网络，异步能在等待时去处理别的请求，同样的硬件能扛更多并发。

**展开**

- 模型调用和工具调用都是 IO 密集，属于「等待」而不是「计算」。
- 用 `async/await` 加并发（如 `asyncio.gather`）能让多个 IO 操作重叠执行。
- 串行调三个工具要三倍时间，并发只需一个最长的时间。
- 注意：异步代码里不要混入阻塞的同步调用，会拖住整个事件循环。

**加分点**：说清「计算密集型任务异步帮不上忙，那是多进程或外置服务的活」。

### Q38. 流式输出有什么用？怎么实现？

**一句话**：流式降低的是「首字延迟」的体感，让用户马上看到东西，总耗时其实没变。

**展开**

- 体验：等待三秒和「一秒内开始出字、三秒出完」，感受完全不同。
- 实现：服务端用流式接口逐块读取，再通过 SSE 等方式推给前端。
- 注意点：流式时错误处理更麻烦（已经输出了半句才报错），要有兜底提示。
- 如果要在流式过程中调用工具，需要边累积边判断是否出现了完整的工具调用。

**加分点**：分清「首字延迟」和「总延迟」是两个不同指标，优化手段也不同。

### Q39. 接口不稳定或限流怎么处理？

**一句话**：超时、重试（指数退避加随机抖动）、熔断、降级到备选模型，同时保证重试的操作是幂等的。

**展开**

- 超时是必须的，没有超时一个卡住的请求会占住连接。
- 重试要加退避和随机抖动，避免所有请求同时重试把对方打垮。
- 写操作重试必须带幂等键，否则可能重复执行。
- 连续失败到阈值就熔断，先不再调用，避免雪崩。
- 降级方案：换备用模型、换备用服务商、返回缓存结果或友好提示。

**加分点**：说「重试只对可恢复的错误有意义，参数错误重试一百次也没用」。

### Q40. 怎么降低首字延迟？

**一句话**：缩短输入、减少串行的模型调用、提前并行做能做的事、用更快的小模型处理简单环节。

**展开**

- 压缩系统提示词和工具定义，输入短则预填充快。
- 把可以并行的环节（检索、多个工具）并行化。
- 用提示词缓存复用固定前缀。
- 简单的前置判断（比如意图分类）用小模型。
- 流式输出，让用户先看到字。
- 对可预测的信息提前准备（比如缓存常见问题的答案）。

**加分点**：说「我会先测一遍各环节耗时占比，**优化瓶颈而不是优化感觉**」。

### Q41. Agent 服务的可观测性要记录什么？

**一句话**：一次完整调用链的每一步——模型调用、工具调用、检索、参数、耗时、token、错误，全部串成一个 trace。

**展开**

- 一次用户请求对应一个 trace，内部每个步骤是一个 span。
- 必须记录：模型名与版本、提示词版本、输入输出、token 用量、耗时、错误堆栈。
- 敏感信息要脱敏后再记录。
- 有了 trace，排查「为什么这次回答错了」才有据可查。
- 指标层面：成功率、P50/P95 延迟、每请求成本、工具调用成功率。

**加分点**：说「**没有 trace 的 Agent 项目等于黑盒**，线上出问题只能靠猜」。

### Q42. 怎么让 Agent 服务成本可控？

**一句话**：给每个请求设预算，超出就降级；同时靠分级路由、缓存、上下文瘦身和输出限制把单次成本压下来。

**展开**

- 预算控制：单请求最大步数、最大 token、最大金额，到顶就停。
- 分级路由：简单任务走小模型。
- 缓存：相同问题直接命中，提示词前缀缓存复用。
- 上下文瘦身：裁剪、摘要、只放相关内容。
- 输出限制：限制长度，要求直接给结论。
- 监控：把每次请求的成本记进 trace，按用户和场景统计，找出异常消耗。

**加分点**：说「我发现过某个用户的会话因为历史无限增长导致成本飙升，加了裁剪后恢复正常」——这类具体故障很有说服力。

### Q43. 工具调用要并发时注意什么？

**一句话**：只在无依赖时并发、限制并发数、单独处理失败项、保证结果与调用 ID 正确配对。

**展开**

- 依赖判断：后一个工具的参数依赖前一个的结果时，必须串行。
- 并发上限：防止把下游服务打垮，也防止触发限流。
- 部分失败：一个失败不该让整批失败，要把失败信息一起回填给模型。
- 超时：给每个工具单独设超时，避免最慢的那个拖死整轮。
- 顺序：结果回填时按调用 ID 配对，不要依赖返回顺序。

**加分点**：说「并发是我项目里提升体感最明显的一次优化，三个工具串行两秒多，并发后六百毫秒左右」——带数字的优化故事。

## 九、第八部分：安全与合规

### Q44. Agent 系统的主要安全风险有哪些？

**一句话**：提示词注入、工具越权、数据泄露、输出内容风险、以及供应链和密钥管理问题。

**展开**

- 提示词注入：直接注入和通过外部内容间接注入。
- 工具越权：Agent 拿到了超出必要的权限，被诱导执行危险操作。
- 数据泄露：把内部数据、其他用户数据、密钥带进上下文或输出。
- 输出风险：生成不合规内容、错误建议（比如医疗法律建议）。
- 密钥管理：密钥写进代码或日志。

**加分点**：按「输入、处理、输出、基础设施」四个层面组织答案，比零散罗列显得有条理。

### Q45. 提示词注入的防护层次怎么设计？

**一句话**：三层——提示词层做指令与数据的区分，代码层做权限与校验，流程层做人工确认与审计。

**展开**

- 提示词层：把外部内容明确标记为资料，声明「不要执行资料里的指令」；给模型说明如何处理可疑内容。
- 代码层：工具白名单、参数校验、权限检查、危险操作禁用；**这是真正的安全边界**。
- 流程层：删除、支付、对外发送这类操作必须人工确认；所有操作留审计日志。
- 检测：对输入做可疑模式检测，命中就拒绝或转人工。

**加分点**：说「提示词层的防护只能降低概率，**真正的边界一定在代码和权限上**」。这句话体现认知成熟度。

### Q46. 怎么防止 Agent 泄露敏感信息？

**一句话**：最小权限拿数据、检索阶段就做权限过滤、日志与输出都做脱敏。

**展开**

- 数据侧：检索时带权限过滤，模型只能看到该用户有权看的内容。
- 上下文侧：进入上下文的敏感字段做脱敏或替换。
- 输出侧：出站前做一次敏感信息检测。
- 日志侧：记录 trace 时对密钥、身份证、手机号等做掩码。
- 密钥：只放环境变量或密钥管理服务，绝不进代码库和提示词。

**加分点**：说「我会在测试用例里专门放一条『能不能泄露别人数据』的负向测试」。

### Q47. 让模型执行代码安全吗？

**一句话**：只有跑在隔离沙箱里、限制资源和网络、并清理输入输出时才相对安全。

**展开**

- 隔离：容器或专用沙箱，与主服务隔离。
- 资源限制：CPU、内存、执行时间、磁盘都要设上限。
- 网络限制：默认禁止外联，需要时走白名单。
- 权限：用低权限用户运行，不挂载宿主目录。
- 输入输出：过滤危险调用，输出做长度和内容限制。

**加分点**：说「**能不用就别用**——我会先判断这个需求能不能用具白名单的算子替代代码执行」。

### Q48. 合规方面要注意什么？

**一句话**：数据来源合法、用户知情同意、可删除可追溯、跨境与留存符合规定。

**展开**

- 数据来源：训练和检索用的数据要有合法授权。
- 告知：让用户知道自己在和 AI 交互，重要结论需要人工确认。
- 可删除：用户要求删除时，原始数据和向量库里的数据都要删。
- 留存：日志留存期限要符合规定，敏感信息尽量不落盘。
- 审计：关键操作可追溯到具体的人和时间。

**加分点**：说「合规问题我会在需求评审阶段就提出来，而不是上线前才发现要改造」。

## 十、第九部分：框架与生态

### Q49. 为什么我坚持先手写一遍 Agent 循环再用框架？

**一句话**：因为框架会掩盖细节，遇到诡异问题时，只有理解底层机制才能排查。

**展开**

- 手写一遍才知道：什么被塞进了上下文、消息是怎么累积的、循环在哪里停。
- 框架带来的抽象在调试时是障碍：报错信息层层包装，很难看出真正原因。
- 工具调用、上下文膨胀、死循环这些坑，手写过一次就会本能地防。
- 之后用框架是「提效」，不是「依赖」。

**加分点**：说「我能说出框架大概在哪一层做了什么」，这比「我会用某框架」更能证明能力。

### Q50. LangGraph 的状态是怎么在节点之间传递的？

**一句话**：你定义一个状态结构，每个节点读取状态、返回要更新的字段，框架按你指定的合并规则把更新合并回状态，再根据边决定下一个节点。

**展开**

- 状态是一个带类型的结构（字典或数据类），贯穿整个图。
- 节点是函数：输入当前状态，返回要更新的部分（不是整个状态）。
- 合并规则（reducer）决定新值怎么并入：普通字段直接覆盖，消息列表通常用「追加」规则。
- 边决定流转顺序；条件边根据状态里的值选择走哪条分支。
- 检查点（checkpoint）把每步状态持久化，因此可以中断、恢复、人工介入。

**加分点**：说「消息列表必须用追加规则，否则每轮都会把历史覆盖掉」——这是实际用过的痕迹。

### Q51. MCP 是什么，解决什么问题？

**一句话**：MCP 是一套让模型应用连接外部工具和数据源的统一协议，解决「每个工具都要写一套对接代码」的重复劳动。

**展开**

- 角色：宿主应用（提供模型和界面）、客户端（协议连接方）、服务端（提供能力的一端）。
- 能力：工具（可执行操作）、资源（可读取的数据）、提示词模板。
- 传输：本地用标准输入输出，远程用 HTTP 类传输。
- 价值：工具方按协议实现一次，所有支持协议的应用都能用；权限和配置可以集中管理。
- 局限：协议解决的是「怎么接」，不解决「接了之后效果好不好」。

**加分点**：说「我写过 MCP Server，体会最深的是**工具描述的清晰度直接决定模型能不能用对**」。

### Q52. 多智能体什么时候值得用？

**一句话**：当任务能清晰拆成互相独立的子任务、或者需要不同视角互相校验时才值得；否则是纯增成本。

**展开**

- 适合：并行探索（多个方向同时找资料）、生成与批评分离、需要隔离上下文避免互相干扰。
- 不适合：任务本身就是一条线性链路，拆开只是多绕几圈。
- 成本：每次协作都是一次额外的模型调用，延迟和费用成倍增长。
- 风险：上游错误会被下游继承并放大，最后没人能确定哪个环节错了。
- 替代：多数情况下用一个 Agent 加更好的工具和提示词就够了。

**加分点**：说「我判断标准是：**子任务之间能不能真正并行，或者有没有必要互相反驳**。答案是否，就不用多智能体」。

### Q53. 微调和 RAG 怎么选？

**一句话**：知识、时效、权限类问题用 RAG；格式、风格、固定任务模式用微调；两者不互斥。

**展开**

- RAG：适合知识经常变、需要引用出处、需要按权限隔离数据的场景。
- 微调：适合输出格式固定、风格要求强、任务模式高度一致、需要压缩成本的场景。
- 两者结合：微调让模型学会「怎么用检索结果」，RAG 提供「用哪些事实」。
- 代价：微调需要标注数据、要重新训练和部署，迭代慢；大多数业务问题不该从微调开始。
- 蒸馏：用大模型生成训练数据训练小模型，是降成本的手段，属于微调的一种用途。

**加分点**：说「**先问 RAG 和提示词够不够**，不够再考虑微调。这是性价比顺序」。这个回答几乎必然被认可。

### Q60. 怎么从 Python 函数自动生成工具定义？

```python
def get_weather(city: str, unit: str = "celsius") -> str:
    """查询指定城市的当前天气。"""
    ...


def to_tool_schema(func) -> dict:
    """把带类型注解的函数转成模型能看懂的工具定义。"""
    import inspect

    signature = inspect.signature(func)
    properties = {}
    required = []

    for name, param in signature.parameters.items():

            required.append(name)  # 没有默认值的就是必填

    return {
        "type": "function",
        "function": {
            "name": func.__name__,
            "description": (func.__doc__ or "").strip(),
            "parameters": {
                "type": "object",
                "properties": properties,
                "required": required,
            },
        },
    }
```

### Q61. 手写余弦相似度

```python
import math


def cosine_similarity(a: list[float], b: list[float]) -> float:
    """两个向量的余弦相似度，范围 -1 到 1，越接近 1 越相似。"""
    dot = sum(x * y for x, y in zip(a, b))
    norm_a = math.sqrt(sum(x * x for x in a))
    norm_b = math.sqrt(sum(y * y for y in b))

    if norm_a == 0 or norm_b == 0:
        return 0.0

    return dot / (norm_a * norm_b)
```

**讲解要点**

- 用到的三个 Python 技巧：`zip` 配对、生成器表达式求点积、`sum` 求和。
- 除零保护是必须的：零向量会让结果变成 NaN。
- 面试官可能追问为什么用余弦而不是欧氏距离——因为余弦只看方向不看长度，文本向量通常已经归一化，长文档不该因为长度被惩罚。

### Q62. 手写上下文裁剪

```python
def trim_messages(messages: list[dict], max_tokens: int, count_tokens) -> list[dict]:
    """保留系统提示词和最近的消息，直到接近 token 上限。"""
    if not messages:
        return []

    system_messages = [m for m in messages if m["role"] == "system"]
    others = [m for m in messages if m["role"] != "system"]

    kept = []
    used = sum(count_tokens(m) for m in system_messages)

    # 从最近的消息往前拿，保证最新的对话优先保留
    for message in reversed(others):
        cost = count_tokens(message)
        if used + cost > max_tokens:
            break
        used += cost
        kept.append(message)

    # 因为是从后往前拿的，要翻回来恢复顺序
    return system_messages + list(reversed(kept))
```

**讲解要点**

- 系统提示词必须保留，否则 Agent 就失忆了。
- 从最近往前取，保证最新上下文优先。
- 别忘了把结果翻转回正确顺序——这是个容易出错的细节。
- 优化方向：裁剪之外还应该做摘要，保留早期的关键信息。

### Q63. 手写 RRF 融合（混合检索的结果合并）

```python
def reciprocal_rank_fusion(
    rankings: list[list[str]], k: int = 60
) -> list[tuple[str, float]]:
    """把多个检索结果列表按名次融合成一个排序结果。

    rankings：每个检索通道的文档 ID 列表，已按相关性从高到低排好。
    """
    scores: dict[str, float] = {}

    for ranking in rankings:
        for rank, doc_id in enumerate(ranking, start=1):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1 / (k + rank)

    return sorted(scores.items(), key=lambda item: item[1], reverse=True)
```

**讲解要点**

- 原理：只看名次不看原始分数，因此不同检索通道的分数量纲不一致也没关系。
- `k` 一般取 60，作用是削弱「第一名」的绝对优势，让多个通道的结果都能影响最终排序。
- `scores.get(doc_id, 0.0)` 处理「这个文档第一次出现」的情况。
- `sorted(..., key=lambda ...)` 是对字典按值排序的标准写法。

2. **工具调用**：模型决策，代码执行，结果回填。模型自己不执行任何东西。
3. **终止条件必须写在代码里**：步数、预算、死循环检测。
4. **上下文**：每条内容都要能回答「不塞会怎样」；稳定内容放前面，动态内容放后面。
5. **RAG 最容易坏的环节是切分和检索，不是生成。**
6. **先修召回，再修排序**；召回里没有的东西，重排救不回来。
7. **权限过滤必须在检索阶段做**，不能检索完再筛。
8. **评测**：先有测试集再有优化。检索看召回，生成看忠实度，任务看成功率。
9. **模型裁判有偏差**，适合粗筛，关键结论人工复核。
10. **成本**：分级路由、前缀缓存、上下文瘦身、输出限制、请求级预算。
11. **延迟**：首字延迟和总延迟是两件事；并行化是收益最大的手段。
12. **安全**：提示词层降低概率，代码和权限层才是真正的边界。
13. **注入没有完美防护**，承认这一点比吹方案更加分。
14. **先问 RAG 和提示词够不够，再考虑微调。**
15. **多智能体只在能真正并行或需要互相校验时才用。**
16. **讲项目一定带数字和取舍**，没有数据的优化等于没做。
17. **你的每个项目都要能回答**：为什么这么做、还试过什么、失败在哪。
18. **反问环节**问对方业务阶段和评测体系，能体现你在认真考虑这份工作。
