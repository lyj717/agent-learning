## 一、三条面试问题（计划表点名要答的）

### 1. 为什么「上下文越用越贵」？

我的回答：

- 每一轮请求实际发出去的是所有历史记录，模型本身没有记忆，所以上下文越长，输入越多
- 20 轮对话的总输入 token 是 12200，而对话内容本身只有 1230，差了将近十倍
- 而且输出比输入贵得多（4 倍），思考 token 也记在输出里——我实测过：1024 个输出 token 全是思考，正文一个字都没有
- 所以上下文会越用越贵

### 2. 长对话你怎么取舍？

我的回答：

- 我会设一个裁剪策略：`MAX_TURNS`（现在是 8 轮），超过这个轮数就把最早的对话丢掉
- 对应的后果是：用户问「一开始说的那件事」，模型就不记得了——这是拿「记得久」换「便宜、快、不爆上下文」
- 另外我做了 `/remember`：用户说「记住这个」，事实就存进本地 `facts.json`，**每次请求前从文件读出来、拼进 system 消息一起发过去**。模型本身没有任何可写的地方——它不记得，是我们每轮喂给它


### 3. 流式输出为什么重要？

我的回答：

- 流式输出并不会改变总的时间，改变的是用户看到第一个字的时间，这对聊天机器人这种工具来说是十分重要的
- 在这个推理模型上，打字机会在模型思考完后开始冒字，因为模型默认采用的是思考模式，在输出之前会先思考一遍
- 如果不采用流式输出，用户会一直等待信息，这对用户来说体验很差

## 三、预习结论（下周是 Week 02：结构化输出与工具调用）

**材料在哪**：官方文档 <https://api-docs.deepseek.com/zh-cn/api/create-chat-completion>
里的 `response_format`、`tools`、`tool_choice` 三节（HANDOFF 里写了要点）。

用两三句回答：

- 「结构化输出」解决的是什么问题？
- 结构化输出的核心优势在于其可机器读取性，这使得LLM的输出能够无缝集成到其他软件系统和数据库中
- 提示词是在「请求」模型，而模式是在「约束」它的输出形状
- 「工具调用」解决的是什么问题？（提示：模型自己不会查天气、也不会算你数据库里的数）
- Tool Calls 让模型能够调用外部工具，来增强自身能力。
- 两者共同的前提是什么？（提示：模型的输出从「给人读」变成「给程序读」）
- 两者都要求**模型的输出能被程序稳定解析**：结构化输出要求内容能 `json.loads` 且符合 schema，工具调用要求函数名和参数能可靠解析出来。解析不了，两条路都走不通——所以最后都要在代码里校验，光靠提示词不行
