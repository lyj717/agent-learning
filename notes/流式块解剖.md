# 流式返回的「块」解剖

> 一次 `stream=True` 的请求，服务端不是给你一整段回答，而是推来一串**块**（chunk）。
> 这份笔记把每个块拆开，说清每个字段干嘛用、什么时候有值。
> 数据是 2026-10-05 在这台机器上真跑出来的（模型 `deepseek-flash`），不是编的。

---

## 怎么用这份笔记

先记住一句话：**你看到的那句完整回答，是你自己一块一块拼出来的。**

写流式代码卡住时，按这三个问题去查：

| 你想知道 | 看哪里 |
|---|---|
| 这一块有没有新内容？ | `chunk.choices[0].delta` |
| 说完了没？被截断了吗？ | `chunk.choices[0].finish_reason` |
| 这次花了多少 token？ | 最后一块的 `chunk.usage` |

---

## 一、底层：原始 SSE 长什么样

用 `httpx` 绕过 SDK 直连同一次请求，看到的是这样：

```
HTTP 200
content-type:       text/event-stream; charset=utf-8
transfer-encoding:  chunked

data: {"id":"dfdbac64-...","object":"chat.completion.chunk",...}
data: {"id":"dfdbac64-...","object":"chat.completion.chunk",...}
...
data: [DONE]
```

- **`text/event-stream`**：走的是 SSE（server-sent events），服务器可以主动一条条推。
- **`transfer-encoding: chunked`**：响应体长度不预先声明，边生成边发——这两条合起来才是
  「能边收边给」的协议基础。
- **`data: ` 后面是 JSON**：一行一个块；`[DONE]` 是结束标记。

SDK 干的活只有一件：把每一行的 JSON 解析成对象，`[DONE]` 直接丢掉不给你。

## 二、一个块的骨架

```
信封（每个块都带，内容基本重复）
├── id                     同一次请求的所有块共用这一个 id
├── object                 "chat.completion.chunk"（非流式是 "chat.completion"）
├── created                时间戳（秒）
├── model                  实际服务的模型名
├── system_fingerprint     后端模型版本指纹
├── usage                  平时是 null，**只有最后一块有值**
└── choices[ ]             数组；流式下通常 1 个元素，**也可能是空的**
    └── [0]
        ├── index                    候选编号（只要一个候选时恒为 0）
        ├── delta                    ← 流式的核心：这一块「新多出来」的部分
        │   ├── role                 "assistant"，只有第 1 块有
        │   ├── content              正文新增（比如 "Token"）
        │   ├── reasoning_content    思考新增（比如 "我们需要"）
        │   ├── tool_calls           工具调用，Week 02 才用
        │   └── refusal              拒答内容，一般 null
        ├── finish_reason            只有最后一块有值："stop"
        └── logprobs                 概率信息，一般不用
```

对照记：非流式那次你读的是 `message`（完整的一句），流式读的是 `delta`（一小截增量）。
**字段名不一样、含义也不一样**，这是最常见的错。

---

## 三、四类块的真实取值

同一次请求里挑出来的四块（`null` 就是「这个字段这一块没值」）：

| | `role` | `content` | `reasoning_content` | `finish_reason` | `usage` |
|---|---|---|---|---|---|
| ① 第 1 块（开场） | `"assistant"` | `null` | `""` | `null` | `null` |
| ② 思考块 | `null` | `null` | `"我们需要"` | `null` | `null` |
| ③ 正文块 | `null` | `"Token"` | `null` | `null` | `null` |
| ④ 最后一块（收尾） | `null` | `""` | `null` | `"stop"` | 完整用量 |

那么一次请求的顺序大致是：

```
① 开场 → ②②②②…（思考，一大串）→ ③③③③…（正文）→ ④ 收尾
```

2026-10-05 实测的那次：**一共 210 块，前 98 块全是思考**（`content` 为 `null`），
第 99 块才开始出正文；最后一块上 `completion_tokens=209`，其中 `reasoning_tokens=178`。

## 四、信封层：每个字段干嘛用

| 字段 | 什么时候有值 | 用途 |
|---|---|---|
| `id` | 每块都有，全相同 | 判断「这些块是不是同一次请求」；写日志时按它归组 |
| `object` | 每块都有 | `chat.completion.chunk` —— 流式的标记 |
| `created` | 每块都有 | 请求时间戳 |
| `model` | 每块都有 | 实际服务的模型名（换成别的模型时用来核对） |
| `system_fingerprint` | 每块都有 | 后端版本指纹。同一串说明没换版本——「同样 prompt 输出变了」时先看它 |
| `usage` | **只有最后一块** | 本次的 token 账：`prompt_tokens` / `completion_tokens` / `reasoning_tokens` 等 |
| `choices` | 每块都有，但**可能为空列表** | 候选回复数组，见下一节 |

**为什么信封要重复？** 让每一块都能自成一体——顺手拿到一块，不用回头找第一块就知道
「这是哪次请求、哪个模型、什么时间」。

**为什么 `usage` 在最后一块？** 因为只有全部生成完了，服务端才知道一共用了多少 token。
官方文档特别说明：**不会单独发一个只含 usage 的块**，统计信息挂在最后一个内容块上。

---

## 五、`choices[0]` 里每个字段干嘛用

| 字段 | 说明 |
|---|---|
| `index` | 候选编号。接口允许一次要多个候选（`n=2`），只要一个时恒为 0 |
| `delta` | **本块新增的内容**，流式的一切都在这里 |
| `delta.role` | 只有第 1 块有（`"assistant"`），后面都是 null——角色不用重复播报 |
| `delta.content` | 正文新增。可能是 `null`（思考阶段、或收尾块），也可能是 `""`（空串） |
| `delta.reasoning_content` | 思考模式专用：推理过程的新增。正文之前那一大片都是它 |
| `delta.tool_calls` | 模型要求调用工具（Week 02 学） |
| `finish_reason` | 只有最后一块有值：`"stop"` 正常说完、`"length"` 被 `max_tokens` 截断、`"tool_calls"` 要调工具 |
| `logprobs` | 每个 token 的概率，一般用不上 |

**`content` 和 `reasoning_content` 是两条并行的流**：思考阶段只有后者有值，正文阶段只有前者有值。

---

## 六、写代码的五条规矩

1. **拼 `delta.content`**，不是 `.message.content`——流式里没有 `message` 这个字段。
2. **`content` 可能是 `None` 或 `""`**：有内容才打印、才拼接（`if piece:`）。
   不判断的话，屏幕上会吐一堆空串，拼接结果看着对、其实多走了很多无用块。
3. **`chunk.choices` 可能是空列表**：先 `if not chunk.choices: continue`，
   不然 `choices[0]` 会 `IndexError`。
4. **`usage` 只在最后一块**：循环里遇到 `chunk.usage is not None` 就收下它
   （记账全靠它，`/cost` 就指望这个）。
5. **判断「说完了」看 `finish_reason`，不要看「有没有收到内容」**——
   思考块也有内容、空 `content` 的块也照来；被 `max_tokens` 截断时是 `"length"`，
   那不是正常结束，半截回答不该当成完整回答存起来。
